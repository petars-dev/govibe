# GoVibe Architecture

This document describes the high-level architecture of the GoVibe web framework skeleton.

## Layers
- Router (chi) wires routes and middleware.
- Controllers contain no business logic; they orchestrate actions/services and render views or APIs.
- Business:
  - actions/: single-function units of business logic
  - services/: packages with richer logic
    - codegraph/: dev-only graph indexer; fills the embedded Cayley store with a model of the project itself (see "Dev-only tooling")
- Storage:
  - mariadb/: DB connectivity (sqlx over database/sql)
  - migrations/: goose v3 SQL migrations embedded in binary
  - dbexplorer/: dev-only schema introspection (per table, and `Snapshot` for the whole schema at once, which feeds the graph's db layer), filtered queries, sampling, explain plans, and gated test-data mutations, backing /dev/db and the db_* MCP tools
  - graphdb/: dev-only embedded Cayley graph store, backing /dev/graph and the graph_query MCP tool
- Views:
  - assets/templates: templ components rendered server-side
  - assets/static: static assets (Tailwind output, images, etc.)
  - assets/htmx: vendored htmx 2.0
- devmcp/: dev-only Model Context Protocol server (official Go SDK), mounted at /dev/mcp over streamable HTTP, exposing the db_* tools and the graph_* agent surface (tools, two resources, one prompt) to local agents

## Requests
1) chi middleware stack -> controller handler
2) controller -> actions/services -> storage as needed
3) controller renders templ page or returns JSON

## Configuration
- Centralized in config/env.yml using ${ENV:default} placeholders.
- Resolved at runtime; typed access via config.Config or dynamic via config.Unmarshal/config.Get.
- `database.type` (`DATABASE_TYPE`, default `mysql`) selects the goose migration dialect via `storage/migrations.SetDialect`. Goose defaults to postgres if never told otherwise, which silently breaks migrations against any other database — every entry point that runs goose (server boot in main.go, `govibe migrate up/status/down`) sets this explicitly instead of relying on that default.

## Logging
- logrus, text formatter by default.

## Dev-only tooling
- `/dev/docs`, `/dev/graph`, `/dev/db`, and `/dev/mcp` are wired directly in routes.go and are only mounted when `!cfg.IsProd()`; none of them exist in a production build.
- `/dev/db` is a Faucet-like database explorer (schema introspection, table browsing, filtered queries, row sampling, explain plans) with an optional, explicitly-gated mutation surface (`db_insert_test_row`/`db_reset_test_data`, or the equivalent `/dev/db/api` endpoints) for seeding/clearing test fixtures. Gated by `dev.db.allow_mutations` in config/env.yml (`DEV_DB_ALLOW_MUTATIONS`), which has no effect in production regardless of the flag.
- `/dev/mcp` mounts an MCP server (github.com/modelcontextprotocol/go-sdk) over streamable HTTP so local agents can call the same db_* tools plus the graph tools without going through the UI. The graph tools are `graph_schema` (start here), `graph_context`, `graph_impact`, `graph_path`, `graph_search`, `graph_neighbors`, `graph_findings`, `graph_reindex`, and `graph_query` (a raw read-only Gizmo query); the resources `govibe://graph/overview` and `govibe://graph/schema`; and the prompt `explain-change`. Each call first brings stale graph layers up to date, then reads the graph into memory (`codegraph.Load`, about 20 ms for 5,000 quads) and answers in Go; nothing is cached, so an answer is always from the graph as it is.
- See docs/specs/SPEC_DEV_DB_EXPLORER.md for details and status.
- The graph store's bolt file (`docs/graph/*.bolt`) is derived data and is git-ignored. What goes into the graph and how to query it is defined in `docs/public/GRAPH_SCHEMA.md`; the plan for the indexer is `docs/specs/SPEC_GRAPH_INDEXER.md`.
- **Graph indexer** (`business/services/codegraph`, Phases 1-5 of that spec): once `routes.NewRouter` has wired everything, a goroutine indexes the project into the graph store, so every Air rebuild/restart refreshes it. It runs inside the server process because the process owns the bolt lock; it never delays startup and a failure is logged, never fatal. `POST /dev/graph/reindex` rebuilds on demand and returns a JSON report (per-layer status, whether it was rebuilt, quad counts, added/removed vs the previous run). Each layer owns the quads carrying its `layer:<name>` label and replaces only those, so quads added by hand survive. Implemented layers: `code` (packages, files, funcs, types, imports from `go/ast`, and the facts the other layers resolve against), `routes` (the live chi router: route → handler by file and line, middleware), `templates` (`.templ` components and who renders them), `config` (`config/env.yml` keys, defaults, environment variables, sensitive flags, and every use in the code), `mcp` (tools registered with `mcp.AddTool`), `db` (the schema from the migrations in `storage/migrations/sql`, merged with the live database's schema read by `dbexplorer.Explorer.Snapshot` when one is configured: tables, columns, indexes, foreign keys, drift between the two, relations the schema implies, and which code reads or writes which table), `docs` (docs, specs and their status rows, what they mention, and what they name that is gone), `findings` (problems derived from all of the above: layering violations, stale doc references, config declared and never read or read and never declared, a table without a primary key, migration drift, ...; a rule that could not run says so), and `meta` (`build:latest` and one `layer:<name>` node per layer). Each layer has a fingerprint over its inputs and its dependencies' fingerprints; a `/dev/graph` page load and every `graph_query` call first rebuild only the stale layers, which is how an edit to `docs/**` (ignored by Air) shows up without a restart. Two **opt-in** layers (Phase 6) are off unless asked for (`dev.graph.calls` / `dev.graph.git`, i.e. `GRAPH_CALLS` / `GRAPH_GIT`, or `graph_reindex` naming the layer, which switches it on until the server restarts): `calls` type-checks the module with `golang.org/x/tools/go/packages` (about a second) and records which function calls which, with calls through an interface the module declares linked to every type that could be on the other end (an annotated edge: method `interface_dispatch`, confidence 80 down to 30), and `git` reads `git log` (newest 1,000 commits, once per `HEAD`) for each file's last commit, churn, number of authors and the files that change in the same commits. A layer that is off has status `off` and holds no quads. Phase 4, the agent surface, is the read side of the same package (`model.go`, `resolve.go`, `agent_*.go`): a `Model` (an in-memory copy of the indexer's quads) with reference resolution (`GET /api/hello`, `controllers/api.go:14`, `orderstore.Store.List`, `orders`), search, neighbors, impact, path and context. With the `calls` layer off, reach beyond what a stored edge ties together is estimated from package imports and labelled so (method `package_imports`, confidence at most 60): a route that imports the code that touches a table is possible, not proven. With it on, `graph_impact`, `graph_path` and `graph_context` walk call edges instead: a route's path to a table is a chain of calls with the weakest hop's confidence, `access` is the union over every call path, "no table is reached" is a measured answer, and the request-flow view and the routes report show the tables each route reaches. The live schema can change with no file changing, so a freshness check reads it too (reused for 5 seconds), and an unreachable database only makes the `db` layer fall back to the migrations. Phase 5, the human surface: `/dev/graph` is a page (`assets/static/graph.js`) that draws bounded views the server builds from the same `Model` (architecture, request flow, database ER, docs against code, config usage, findings, or the neighbourhood of any node) and never loads the whole graph, so it stays quick at any size; its data is `/dev/graph/data/{status,view,node,search,findings,table}` (`controllers.GraphUI`). `/dev/graph/reports/{routes,config,schema,layers}` are reference pages generated from the graph on every load, so the route table, config reference, schema listing and package layer map cannot drift from the code. The layering rule the findings enforce is `layering.go`: only business may call storage, storage depends on nothing above it, business does not depend on the HTTP layer; `routes`, `main`, `cmd` and `devmcp` may import anything. `govibe graph index` (`cmd/govibe/cmd_graph.go`) builds the same graph offline, into a store of its own (`--dir`), for when no server holds the lock; with `--fail-on error --baseline docs/graph/baseline.json` it exits 1 on a finding the baseline does not accept, which is what `.github/workflows/graph.yml` runs on every push to `main` and every pull request (`make graph-check` locally). Production never opens the graph store, so it never indexes.
