# S4: the `tool` directive (`go get -tool` for govibe, templ, air)

Machine: Apple M1 Pro, 8 cores, go1.26.5 darwin/arm64. Everything ran in `$SPIKES/s4` (app `example.com/shop`) against `$SPIKES/s4fw`
(an rsync of the repo, module renamed to `github.com/petars-dev/govibe`, plus `version` and `probe` commands) through `replace`.
Throwaway `GOCACHE`/`GOMODCACHE` directories under `$SPIKES/s4`; the user's caches were not cleared.
No app binary that opens a database was run (the toy app only calls `config.Load()`); `MARIADB_DSN`, `CODE_REVIEW_DB_DSN` and `WORKOS_*` were unset for every run after the coordinator's notice.

## Result in one line
`go get -tool` works with a `replace`, runs from the app directory and costs 0.3 s warm. It also (1) bumps the app's `go` line to 1.26.0 if templ/air are added at `@latest`,
(2) lists the whole dev stack in the app's `go.mod`, and (3) raises shared dependency versions above what the framework was tested with.
The framework's codegraph and controllers tests still pass at the raised versions.

## Commands
```
# app go.mod written by hand: require github.com/petars-dev/govibe v0.0.0, replace => ../../s4fw
go get -tool github.com/petars-dev/govibe/cmd/govibe
go get -tool github.com/a-h/templ/cmd/templ
go get -tool github.com/air-verse/air          # current path; cosmtrek/air is the old name (same versions, module is air-verse/air)
go mod tidy
go tool govibe version | go tool templ version | go tool air -v
```

| after `-tool govibe` | 70 | 436 | 58 | 1.25.0 |

- `go get -tool` of templ and air left go.sum incomplete for the govibe tool: `go tool govibe` failed with "missing go.sum entry for module providing package github.com/yuin/goldmark ..." until `go mod tidy` ran (+149 go.sum lines). The tidy step in the spec's `govibe new` sequence is mandatory, not cosmetic.
- Of the 82 indirect modules only `gopkg.in/yaml.v3` provides a package linked by the app's default build. The default build stays at **70 packages** and has **0** of cayley/MCP/x-tools/goldmark/chroma (`go list -deps . | grep -cE 'cayley|modelcontextprotocol|x/tools|goldmark|chroma'` = 0). The default build is unaffected; only `go.mod` is.
- The seven stack modules the spec names are all listed as indirect: chroma/v2 v2.27.0, cayley v0.7.7, cayley/quad v1.1.0, modelcontextprotocol/go-sdk v1.8.0, goldmark v1.8.2, goldmark-highlighting/v2, golang.org/x/tools v0.51.0.
- Who needs what (modules, from `go list -deps` of each tool package, minus the toy app's own): 41 only for the govibe tool (this includes chi, mysql, sqlx, goose, logrus, which a real app links anyway), **15 only for air** (including `github.com/gohugoio/hugo v0.164.0`, `bep/golibsass`, `bep/godartsass`, `afero`, `go-toml`), 4 only for templ, 13 shared.

## Go toolchain behavior
- `go mod init` writes the running toolchain's version (`go 1.26.5`), not 1.25. The scaffold must write the `go` line itself.
- `go get -tool github.com/a-h/templ/cmd/templ` (latest v0.3.1070, `go 1.26.0`) **silently rewrote `go 1.25.0` to `go 1.26.0`**. No `toolchain` line was added, with the local 1.26.5 toolchain and with `GOTOOLCHAIN=go1.25.14+auto`. Latest air v1.67.4 also needs `go 1.26.0`.
- With `GOTOOLCHAIN=go1.25.14` (no switching) the same command fails and leaves go.mod unchanged: `templ@v0.3.1070 requires go >= 1.26.0 (running go 1.25.14; GOTOOLCHAIN=go1.25.14)`.
- Go lines of releases: templ v0.3.1020 = 1.25.0, v0.3.1070 = 1.26.0; air v1.62.0 = 1.24, v1.63.0 to v1.67.0 = 1.25, v1.67.4 = 1.26.0 (v1.67.1 to v1.67.3 not checked).
- Pinning templ v0.3.1020 and air v1.67.0 keeps `go 1.25.0`, builds and runs on go1.25.14 (`go tool govibe version`, 29 s cold).
- The framework's own `go.mod` requires templ v0.3.1020 for the runtime. With the tool directive the CLI and the runtime are the same templ version by construction; the old Makefile's `go install templ@latest` could not promise that.

## Timing (cold = empty GOCACHE, modules already downloaded; each tool measured with its own fresh GOCACHE)
| Tool | cold | 2nd run | steady warm | cached binary | GOCACHE after |
| --- | --- | --- | --- | --- | --- |
| `go tool govibe version` | 41.7 s | 2.7 s | 0.34 s | 30.1 MB | 365 MB |
| `go tool templ version` | 23.2 s | 1.1 s | 0.26 s | 13.8 MB | 202 MB |
| `go tool air -v` | 20.6 s | 0.8 s | 0.20 s | 10.3 MB | 181 MB |

- Fully cold machine (empty GOMODCACHE and GOCACHE, one shared cache): `go mod download` 13.9 s (301 MB), then govibe 24.6 s, templ 4.9 s, air 4.8 s: **about 48 s total**, GOCACHE 447 MB. Warm again right after: govibe 2.3 s, then 0.3 s steady.
- Steady-state `go tool` wrapper overhead is about 0.3 s over running the cached executable directly (`go tool -n govibe` prints its path; direct exec 0.02 s).
- `go tool govibe graph index --help` (startup only): 0.31 to 0.48 s warm.
- Editing the replaced framework's tool source forces a rebuild: 7.2 s, then 1.0 s, then 0.37 s (contributors only; a tagged module version comes from the module cache and does not change).
- The 60 s fallback threshold was **not reached** (worst cold build 41.7 s on 8 cores; user CPU was 60 s over 29 s wall, so a 2-core CI runner is plausibly 30 to 60 s, an estimate, not measured). The `go install` fallback was not measured. Caching GOCACHE in CI removes it.
- For comparison, `go install` of the same CLI into a scratch GOBIN produced a 40.6 MB binary (the cached `go tool` one is 30.1 MB; reason not investigated).

## Works with `replace`, sees the app
- `go tool` with a `replace ... => ../../s4fw` works. Unrenamed `petars-dev/govibe` (no dot) also worked, but only because of the `replace`; it is not fetchable (S7).
- `go tool govibe probe` inside the app directory (and in `app/sub/dir`): cwd is the invoking directory; `go list -m -json github.com/petars-dev/govibe` resolves the pin; `packages.Load` with `-tags=govibe_dev` found `example.com/shop` in 109 to 192 ms.
- Version skew: a global `govibe` (built with `-X main.toolVersion=v0.2.0`) run in the same app printed `SKEW: tool "v0.2.0" != pinned "v0.0.0"` only because the probe compares them; nothing in `go` does. A global binary is also built against the framework's own go.mod versions (x/tools v0.42.0, goldmark v1.7.4), not the app's (v0.51.0, v1.8.2). The check has to be written (`doctor`, T7.1 shim).

## Version drift caused by tool dependencies
17 shared modules in the app's `go.mod` are newer than the framework's own `go.mod`: templ v0.3.1020 to v0.3.1070, x/tools v0.42.0 to v0.51.0, goldmark v1.7.4 to v1.8.2, chroma/v2 v2.2.0 to v2.27.0, cobra v1.8.0 to v1.10.2, pflag, regexp2, x/crypto, x/mod, x/oauth2, x/sync, x/sys, x/term, x/text, protobuf, go-internal, godotenv.
Evidence it is survivable: the framework's `codegraph/...` tests (goldens included) and `controllers/...` tests, run from the app module so they build with the raised versions, passed (`ok codegraph 33.7s`, `ok controllers 12.3s`).

## Consequence for the design
1. The scaffold must **pin tool versions** (`go get -tool ...@<version>` matching the framework's tested set), not `@latest`, or the generated app's `go` line jumps to 1.26.0 and the spec's "Go version in generated apps is the framework's" is false. Alternatively the framework moves to `go 1.26.0` and says so. Decision needed before Phase 5.
2. Phase 5's step list stands, with `go mod tidy` after the `-tool` calls (go.sum is incomplete otherwise) and an explicit `go` line.
3. air brings Hugo and about 15 modules into every app's `go.mod`; D8 (pin air as a tool) is workable but heavier than the spec assumes. A smaller watcher, or air installed by the Makefile, is an option for D8.
4. The accepted risk "the app's go.mod lists the dev dependencies as indirect" is confirmed in size: 82 indirect modules, 98 / 664 lines. The default build is clean (70 packages).
5. The keystone CI job (T5.6) must build and test the generated app with the versions the app resolves, not the framework's `go.mod`; the codegraph and controllers tests passing at the raised versions is the first evidence.
6. The cold start (about 25 to 42 s once, then 0.3 s) is acceptable; no fallback needed. The T7.1 shim is still needed for the global `govibe` to avoid version skew.
