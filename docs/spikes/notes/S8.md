# S8: scheduler engine (own runner over the `robfig/cron/v3` parser vs `gocron` v2)

Everything ran in `$SPIKES/s8` (module `example.com/s8`, go 1.25.0, toolchain go1.26.5). Raw outputs next to this file's directory:
`s8/dst-robfig.txt` (Next sequences around transitions), `s8/runner-test.txt` (own runner tests), `s8/gc-test.txt` and `s8/all-tests.txt` (gocron tests),
code in `s8/main.go`, `s8/runner/` (runner, fake clock, tests), `s8/gc/gc_test.go`. No binary opened a database; `MARIADB_DSN`, `CODE_REVIEW_DB_DSN` and `WORKOS_*` were unset.

## Recommendation
**Keep D14: own runner over the `robfig/cron/v3` parser, behind `internal/scheduler`.**
The parser is not a differentiator: gocron v2.22.0 *depends on* `robfig/cron/v3 v3.0.1` for cron parsing, so both options inherit the same grammar and the same gaps.
The differences are in the engine, and the ones that matter to this spec favour owning it:
1. gocron's fall-back de-duplication is applied to every cron spec and cannot be turned off, so an hourly `30 * * * *` job **lost one real hour** across the New York fall-back (4 fires in 5 real hours; ours fires 5). It sits in `cronJob.next`, above the pluggable `Cron` interface, so `WithCronImplementation` cannot reach it.
2. gocron has no per-job timeout; the task's `context.Context` carries no deadline (verified). We would write the timeout wrapper anyway.
3. `Job.NextRun()` is zero before `Start()` and can be stale while a run is in flight. Offline `Next` (for `schedule list`) works only through the `Cron` wrapper, i.e. through robfig again.
4. Tests: a 57-line fake clock gives deterministic tests (9 tests, 1.4 s with `-race`, 10 repeated runs, no flakes); gocron with clockwork needs real sleeps between advances (about 8 to 20 ms per step) and its DST test took 20.8 s.
Cost of owning it: **183 code lines** for the runner (validation, overlap, timeout, panic, shutdown, results, DST de-duplication; the per-task loop itself is about 35) plus a 57-line test clock. Weight: +0.61 MB stripped binary and 1 module, against +1.06 MB and 4 modules for gocron.

**What would flip it to gocron:** wanting daily/weekly/monthly job definitions, randomized intervals, cross-job concurrency limits, lockers/electors or a monitor ecosystem out of the box; the team deciding that the hourly fall-back loss is acceptable and preferring fewer owned lines; or robfig's parser failing on something real (it has had no release since 2020-01-04). gocron is actively maintained (v2.19.0 on 2025-12-10, then v2.19.1 2026-01-28, v2.20.0 2026-04-02, v2.21.0 2026-04-13, v2.21.1 2026-04-20, v2.21.2 2026-05-12, **v2.22.0 2026-07-09**), so this is a defensible alternative, not a bad one. I did not read either project's issue tracker.

## Parser behavior (robfig, `cron.NewParser(Minute|Hour|Dom|Month|Dow|Descriptor)`, same as `cron.ParseStandard`)
Valid, from `2026-10-11 18:17:43.123456789 UTC`:
`@hourly` 19:00, `@daily`/`@midnight` next 00:00, `@weekly` Sun 10-18 00:00, `@monthly` 11-01, `@yearly`/`@annually` 2027-01-01, `*/5 * * * *` 18:20, `0 2 * * *` 10-12 02:00, `0 9 * * MON-FRI` works, `TZ=` and `CRON_TZ=` prefixes both work.
- `@every 6h` from 18:17:43.123 gives 00:17:43 (fractional seconds dropped). It counts from the time passed to `Next`. In a runner that is process start.
- **Time zone:** with no prefix the schedule is evaluated in the location of the time passed to `Next` (`0 9 * * *` gives 09:00 in UTC, in Sofia and in New York callers). So a default `scheduler.timezone` means calling `Next(now.In(loc))`. A `CRON_TZ=` prefix wins over the caller's location and the result comes back in the caller's location. gocron's `WithLocation` does the same by prepending `CRON_TZ=<zone>`.
- **dom/dow:** both restricted means OR: `0 0 13 * 5` fires on Fridays *and* on the 13th (Fri 11-06, 11-13, ..., Sun 12-13). A stepped field also counts as restricted: `0 0 */2 * 5` fired Tue 11-03, Thu 11-05, Fri 11-06, Sat 11-07, Mon 11-09 (odd days OR Fridays). Document it.
- Not supported: `L`, Sunday as `7` (`0 0 * * 7` is rejected), seconds. `?` is accepted as `*`.

Invalid and surprising specs (exact messages; robfig names the problem but not the spec or command):
| Spec | robfig result |
| --- | --- |
| `* * *` | `expected exactly 5 fields, found 3: [* * *]` |
| `61 * * * *` | `end of range (61) above maximum (59): 61` |
| `@every` | `unrecognized descriptor: @every` |
| `@weekly2` | `unrecognized descriptor: @weekly2` |
| `CRON_TZ=Nowhere/Land * * * * *` | `provided bad location Nowhere/Land: unknown time zone Nowhere/Land` |
| `0 0 9 * * *` (six fields) | `expected exactly 5 fields, found 6: [0 0 9 * * *]` |
| `""` / `"   "` | `empty spec string` / `expected exactly 5 fields, found 0: []` |
| `*/0 * * * *`, `5-1 * * * *`, `* * * * 8`, `@every banana` | `step of range should be a positive number: */0`, `beginning of range (5) beyond end of range (1): 5-1`, `end of range (8) above maximum (6): 8`, `failed to parse duration @every banana: ...` |
| **`CRON_TZ=Europe/Sofia`** (prefix, no fields) | **panics**: `runtime error: slice bounds out of range [:-1]` (parser.go:99). In gocron the panic escapes `NewJob` to the caller. |
| **`@every 0s`, `@every -5m`, `@every 500ms`, `@every 30s`** | accepted. 0, negative and sub-second become 1 s (30 s stays 30 s). gocron accepts them too. |
| **`0 0 31 2 *`** | parses; `Next` is the zero time (never fires). gocron's `NewJob` rejects it with `ErrCronJobInvalid` ("invalid crontab"); robfig alone does not. |

My `runner.Parse` wrapper (recover, bare-prefix check, `@every` minimum, never-fires check) turns every row above into `command orders:export: invalid schedule "<spec>": <reason>` at `Start`, and all eleven cases are rejected in `TestInvalidSpecsFailStartNamingTheCommand`. The `@every` minimum of 1 m is my choice for the spike; the spec does not set one.
gocron's `NewJob` error for a bad spec reads `gocron: CronJob: crontab parse failure` followed by the robfig message, and does not include the job name.

## DST (robfig `Next`; gocron's default `Cron` is the same code)
Raw sequences are in `s8/dst-robfig.txt`. Dates are 2026: Sofia gap 03-29 (03:00 to 04:00), repeat 10-25 (03:00 to 04:00); New York gap 03-08 (02:00 to 03:00), repeat 11-01 (01:00 to 02:00); Lord Howe has a 30-minute shift (gap 10-04 02:00 to 02:30, repeat 04-05 01:30 to 02:00); Kolkata +05:30 has no DST.
| Case | Raw robfig |
| --- | --- |
| Daily at a time inside the **gap** (Sofia 03:30, NY 02:30, Lord Howe 02:15) | skipped that day, no catch-up |
| Daily at a time inside the **repeat** (Sofia 03:30, NY 01:30, Lord Howe 01:45) | fires **twice** (both offsets) |
| Wildcard hour (`0 * * * *`, `30 * * * *`) | follows real hours: each hour of the repeat fires, the non-existent hour is skipped. At Lord Howe's fall-back `0 * * * *` fires 14:00Z then 15:30Z (the local :00 does not recur) |
| Kolkata `0 * * * *`, `0 9 * * *` | :30 UTC every hour; 03:30 UTC daily. Fine |
| `@daily` in New York over spring-forward | midnight local each day, offset changes |
| `CRON_TZ=Europe/Sofia 30 3 * * *` with a UTC caller | correct, result returned in UTC |

**Own runner** de-duplicates by wall clock only when both the hour and the minute field are fixed (no `*`, `/`, `?`). Tests (fake clock, all pass): Sofia gap daily 03:30 over 03-27..03-31 gives 3 fires (03-29 skipped); Sofia repeat daily 03:30 over 10-24..10-27 gives 3 fires, once per day, while the raw control (`RawDST: true`) gives 4; NY repeat daily 01:30 gives 2 fires in 2 days; NY hourly `30 * * * *` across the fall-back gives 5 fires in 5 real hours (01:30 EDT, 01:30 EST, 02:30, 03:30, 04:30); `CRON_TZ=Europe/Sofia` under a UTC default gives 3 fires in 3 days.
**gocron v2.22.0:** `cronJob.next` (job.go:1241 to 1262) already drops a second occurrence of an identical wall-clock reading. Sofia repeat daily 03:30 gave 3 fires in 3 days (same as ours), the gap day was skipped. But the rule applies to every spec: NY hourly `30 * * * *` fired 4 times in 5 real hours (`01:30 EDT, 02:30, 03:30, 04:30 EST`), losing 01:30 EST. `WithDaylightSavingsTimePolicy(DaylightSavingsTimeRunAfterTransition)` exists for catch-up on gap days (job.go:785 to 794, 1265 to 1285); I read it but did not run it. My `dedupeCron` through `WithCronImplementation` made no observable difference, because gocron already de-duplicates above it.

## Own runner vs gocron: behaviors the spec lists
| Behavior | Own runner (`runner/`) | gocron v2.22.0 + clockwork fake clock |
| --- | --- | --- |
| `*/5 * * * *` from 12:02, advance 1 h | 12 fires, 12:05 to 13:00 | 12 fires, 12:05 to 13:00 |
| `@every 10m` from 12:02:30 | 12:12:30, 12:22:30, 12:32:30 | `DurationJob(10m)`: same |
| Overlap skip | `Skip`: 1 started, 2 recorded as `skipped`; `Allow`: 3 concurrent | `WithSingletonMode(LimitModeReschedule)`: 1 started; a `Monitor` (`WithMonitor`) sees `singleton_rescheduled:2` |
| Timeout | context deadline; cooperative returns `timeout`; a task that ignores the context returns later and is `overrun`, and keeps its slot | no per-job timeout; `ctx` given to the task has no deadline |
| Panic | recovered, status `panic`, later runs go on (`[panic error ok]`) | recovered (`callJobWithRecover`), `AfterJobRunsWithPanic` fired once, 3 runs |
| Shutdown | `Stop(timeout)` returns unclean after the timeout with a task still running | `WithStopTimeout` + `Shutdown()` returns `gocron: timed out waiting for jobs to finish` after the fake clock passes it |
| Offline `Next` for `schedule list` | `Schedule.Next(t)`, pure, no engine | `job.NextRun()` is zero before `Start()`; `gocron.NewDefaultCron(false)` with `IsValid` and `Next` works offline (it is robfig underneath) |
| Invalid spec at boot | wrapper names the command | `NewJob` error lacks the job name; bare `CRON_TZ=Zone` panics |
Correction to my own first draft: I wrote in a test log that gocron gives no signal for a skipped overlap. That was wrong; the `Monitor` reports it, as the table says.

## Consequence for the design
1. D14 holds, with a wrapper around the parser. The spec's "an invalid spec is an error that names the command" needs these rules written down: recover from the parser (bare `CRON_TZ=Zone` panics), reject a spec that never fires (`0 0 31 2 *`), and set a minimum for `@every` (0 s, negative and sub-second silently become 1 s; I used 1 m).
2. `schedule list` cannot print a real NEXT RUN for `@every`: it counts from the server's start time, which an offline command does not know. The spec's example row (`reports:digest @every 6h` with a date) should print "6h after start" or label the date "if started now".
3. The spec needs a DST paragraph (it has none): **gap: skipped, nothing caught up** (consistent with "Missed runs"); **repeat: a spec with fixed hour and minute fires once; a wildcard hour follows real hours**. That is what the runner implements and tests. gocron's rule would lose an hour of hourly jobs.
4. Update the spec's engine paragraph: gocron's latest is v2.22.0 (2026-07-09), not v2.19.0; its next-run is pluggable through `Cron` / `WithCronImplementation`, but its fall-back de-duplication is not; robfig's last release is 2020-01-04 and gocron itself depends on it.
5. Document the dom/dow rule (OR, including stepped fields), Sunday as 0, no `L`, and timezone precedence (`CRON_TZ=` beats `scheduler.timezone`).
6. T4.1's fake clock and tests have a working starting point in `s8/runner/` (runner 183 code lines, fake clock 57, 9 tests).
