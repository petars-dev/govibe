# S9 — Scope: one origin filter in the `Model`

Question (SPEC_FRAMEWORK_EXTRACTION, "Project profile and an app-only graph"): does a single origin filter
applied once in the `Model` (drop nodes of other origins and every edge that touches them) make the
`/dev/graph/data/*` views, the `/dev/graph/reports/*` pages, the findings and every `graph_*` tool
scope-correct "with no per-view logic"?

**Verdict: the read side holds, the claim as written does not.** Everything that reads through `Model` is
scope-correct for free. Findings, three raw store paths, the bookkeeping counters, four "empty means not
built" notes, the not-found errors and seven pre-existing `dev_only` sites are not covered by the filter, and
a global default scope is unsafe. Details and the exact amendment are at the end.

Where classification is not path-derived: `config_key` and `env_var` have three sources (the framework manifest, else the declaring `env.yml`,
else the reader), so an app key that is read but undeclared still gets an origin. Leaf origins (file, package, key, tool, doc, table,
migration) should be written by the layers as an `origin` quad (that is also what makes B1 filterable); edge-derived origins (func, type, route, finding,
annotation, spec_item) belong in the `Model`, as in the prototype. The mixed packages (`controllers`, `routes`) are an artifact of this repo: in an app
one package has one origin.

## 4. Where the filter must live, and "n hidden"

- **Filter: the `Model` constructor, with the scope as an argument** (`Load(ctx, qs, scope)`), applied after the whole graph is classified
  (derived origins need the unfiltered edges). It is not an accessor filter: accessors are used in 70+ places (`m.nodes[...]` directly in 60 sites), so
  filtering the structure once is the only way not to touch them. This was confirmed: no view, report or tool needed a line changed to be scope-correct.
- **The findings layer builds on `all`** (`loadModel` unscoped, as it is now) and findings are filtered by the origin of their `about` node, like any node.
  The gate and baseline load `all`.
- **"n hidden" comes for free**: `applyScope` counts what it drops (nodes, by kind, edges, quads) in the same pass; exposing it is one field on `Status`.
  Caveat: neutral `layer`/`build` counters are global (W3), and "nodes hidden" overstates the picture here because this repo's framework code is in the tree;
  in an app only the router, middleware, manifest keys, tools and external nodes are framework.

## Consequence for the design

The spec's claim "applied once, in the `Model` … so the views, the reports, the findings and the agent tools need no per-view logic" **holds for views,
reports and agent tools and fails for findings and for anything that does not read the `Model`.** Amend T3.3 and the "Scope" paragraph to say:

1. `Load(ctx, qs, scope)`: scope is a parameter, never a global; the app map, reports and `graph_*` tools pass the request's scope, the **findings layer and the gate always pass `all`**.
2. Findings are computed once on `all`; a finding's origin is its `about` target's; a cross-origin finding (`framework.import`, `layering` into a framework package) is an app
   finding whose message and `path:line` carry the evidence, since the framework target is hidden (W2).
3. Layers write `origin` as a quad for leaf kinds (so raw queries can filter); the `Model` derives it for edge-derived kinds. Config keys take the manifest, then the declaring file, then the reader.
4. The `Model` keeps a hidden index (`id → origin`, counts by kind): "n hidden", "exists in scope X" errors, and the `Hidden` block on `Status`.
5. Replace the four "empty means not built" inferences with `layerStatus`; show layer and build counters only for `all`; build `graph_schema` examples from the scoped model.
6. Retire `dev_only` per-view logic in favour of origin (7 sites) in the same change, so there is one notion of "framework".
7. List `graph_query`, the Cayley HTTP API (which can write) and `ManualView` as deliberately unscoped, and say so in their descriptions; `/dev/docs` needs its own switch (T3.9).

## Incident (disclose)

The shell exports `MARIADB_DSN` (and `CODE_REVIEW_DB_DSN`) pointing at the local MariaDB. My first two scratch servers inherited it and **connected to the real
`govibe` database**: goose logged `no migrations to run. current version: 1` (nothing applied), the explorer ran with `mutations=false` and only read the schema.
No write was made, but it broke the isolation rule. Those two runs are set aside in `s9out/run1_with_real_db`; all numbers above are from hermetic runs with the
DB variables unset (`env -u MARIADB_DSN -u CODE_REVIEW_DB_DSN`). **Any other spike that boots a dev server from this shell has the same exposure.**

Two follow-ups after the coordinator's safety message: (1) the hermetic runs unset the DB variables but **not `WORKOS_API_KEY`/`WORKOS_CLIENT_ID`**, so all six scratch
servers logged `workos client initialized`. `main.go` only constructs the client and discards it (constraint 3 of the spec), so no request left the machine, but the
credentials were loaded into the process. (2) While diagnosing, I ran an `env | grep` that printed the local DSN value, credentials included, into this session's
transcript once; it is not in any file I wrote (checked). No server is running now (`:18094` closed, no `s9out/server` process). Any further boot must start with
`unset MARIADB_DSN CODE_REVIEW_DB_DSN WORKOS_API_KEY WORKOS_CLIENT_ID`.
