# S10: Option D, the out-of-process dev host (Phase 7, T7.2)

**Question.** Should the dev panel and the MCP server move out of the app process into a supervisor (`govibe dev`) that builds and runs the
app, hosts the panel itself and proxies to the app? Option D in `docs/specs/SPEC_FRAMEWORK_EXTRACTION.md`, deferred from Phase 0 to here. The
promised benefit: a panel and an MCP server that survive a failing build, which is exactly when an agent needs them; the costs: a supervisor, a
proxy, and a rewrite of the two assumptions the dev tools make today, the live `chi` router in the same process and one process owning the bolt
lock. Output is a decision, not code.

**Method.** Three measurements in scratch modules (nothing touched the working tree, no server of the repository ran), on this machine
(2026-10-18, macOS, Go 1.25), plus a reading of what Air does today when a build fails.

## 1. Proxy cost
A backend answering the Hello JSON and an `httputil.ReverseProxy` (the stdlib, which is what a supervisor would use) on another loopback
port; 20,000 requests each, keep-alive, through `net/http`'s client.

| Path | Concurrency | p50 | p90 | p99 | Throughput |
| --- | --- | --- | --- | --- | --- |
| direct | 1 | 51 µs | 76 µs | 121 µs | 18,000 req/s |
| through the proxy | 1 | 113 µs | 158 µs | 294 µs | 8,300 req/s |
| direct | 8 | 111 µs | 189 µs | 428 µs | 63,500 req/s |
| through the proxy | 8 | 361 µs | 792 µs | 1.03 ms | 18,100 req/s |

About 60 µs per request sequentially, and a 2.2 to 3.5 times drop in throughput of a handler that does nothing; a real handler (a template,
a query) is one to three orders of magnitude slower than that, so the proxy would not be felt during development. **Not a reason to say no.**

## 2. The bolt lock
bolt takes a file lock on `Open` and holds it until `Close`. A second `Open` of the same file from another process, with a timeout, times out,
and so does a **read-only** open (measured: `timeout` after 509 ms and 508 ms; an open after the first `Close` succeeds in 1 ms). So a
supervisor cannot share the graph store with a running app process: either the supervisor owns the store and the app has no graph (the app
process needs none: the indexer, the pages and the MCP server would all be in the supervisor), or they use two stores. The first is the
coherent design; it means **everything that reads the graph moves to the supervisor**, and the app process keeps only what needs the live
process: the router walk (`inspect --json` already replaces it offline), the scheduler status and the database pool for the explorer (a second
pool in the supervisor, or a small introspection endpoint on the app). The dev tools already depend only on the ports they declare (`Deps`), so
the move is possible; it is not small.

## 3. A failing build today
Air's engine (`runner/engine.go`, v1.67.0): on a build error with `stop_on_error = true` (what the scaffold's `.air.toml` sets) it calls
`stopBin()` and returns, so **the old binary is stopped and nothing serves**: no app, no `/dev`, no `/dev/mcp`, until the next successful build.
With `stop_on_error = false` the old binary keeps running the previous code, with its panel and its graph of the previous source (stale, and
labelled as such by the freshness check, which cannot rebuild the `code` layer of a tree that does not parse). So today a broken build means
a dark panel, and flipping one setting means a stale one. Option D would give a live panel over a broken tree: the graph's `code` layer would
report the parse error as a layer failure and the rest (docs, findings from the last good layers, the MCP resources) would answer.

## What an agent needs when the build is broken
The graph (what calls what, where a route goes), the findings, the rules (`govibe://skill`), the docs. All of it comes from **source and the
last `inspect --json`**, none of it from the running process; the only things that need the process are the scheduler's live status and the
database explorer's live schema. So the benefit of Option D does not require Option D: it requires **the graph tools without the app**, which
the tool already has in `govibe graph index` (a scratch store, no server) and could serve over MCP from the tool itself.

## Decision
**Option C stays for v1; Option D is not built.** The resilience it buys is real but narrow, the proxy is cheap, and the lock makes the design
a move of the whole dev stack into a second process with its own lifecycle, not an addition. The cheaper way to the same benefit goes on the
backlog instead: **`govibe mcp`**, a stdio MCP server in the tool that indexes the project into a scratch store and serves the `graph_*` tools,
`govibe://skill`, `govibe://app/manifest` (from the last `inspect --json`) and the framework docs, with no server running and whatever the
state of the build. It needs no proxy, no supervisor and no change to the app process, and an agent configures it once next to the app's
`/dev/mcp`. `stop_on_error` stays `true` in the scaffold: a stale panel that looks live is worse than a dark one with a build error on the terminal.

| Criterion | Option C (today) | Option D | `govibe mcp` (backlog) |
| --- | --- | --- | --- |
| Panel and MCP while the build is broken | no (dark) | yes | MCP yes, panel no |
| Request overhead in development | none | about 60 µs, throughput halved | none |
| Processes | one | two, plus a proxy | one, plus the tool when an agent asks |
| Graph store ownership | the app process | the supervisor; the app process has no graph | a scratch store per run |
| Live router, scheduler status, DB schema | in process | over an introspection endpoint or a second pool | from `inspect --json`; no live status |
| Work | done | a supervisor, a proxy, a second host for `devtools.Mount`, a new lifecycle | a command in the tool over existing packages |
